# Fictional Example: Software Request Workflow

This example uses a fictional organization and contains no private company information.

## Starting Idea

> Make a diagram showing how ExampleCo handles a new software request. An employee submits it, the manager checks the need and budget, Information Security reviews risk, and IT either sets it up or explains why it was declined. Leaders should quickly see the decision points and who owns each step.

## Companion Recommendation

Use a left-to-right swimlane flowchart. It makes ownership and decision points visible without turning the diagram into a policy document.

## Diagram Brief

- **Audience:** Department leaders and employees requesting software.
- **Takeaway:** Requests move through a clear sequence, with the manager owning business approval and Information Security owning risk approval.
- **Type:** Swimlane flowchart.
- **Lanes:** Employee, Manager, Information Security, and IT.
- **Flow:** Submit request → Check need and budget → Review security risk → Approve or decline → Set up software or explain the decision.
- **Decision points:** Need and budget approved? Security risk acceptable?
- **Visible exception:** A declined request returns to the employee with a short reason.
- **Leave out:** Internal policy numbers, tool-specific form fields, and behind-the-scenes planning notes.
- **Rendering direction:** Keep labels short, emphasize the two approval decisions, and end with one of two clear outcomes.

The companion would pass this compact brief to Diagram Design. The finished diagram should not include headings such as “Audience,” “Leave out,” or “Rendering direction.”
